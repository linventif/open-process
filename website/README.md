# Open Process website — Astro, TypeScript and Bun

One Cloudflare Pages project serves the presentation site and application:

- <https://open-process.linv.dev/>: English HTML generated by Astro (default).
- <https://open-process.linv.dev/fr/>: French on its own route.
- <https://open-process.linv.dev/es/>: Spanish using the same components and typed translations.
- <https://open-process.linv.dev/app/>: the Rust application compiled to WebAssembly.

## Development

Install Bun 1.4.0 and Node.js 24, then:

```sh
cd website
bun install --frozen-lockfile
bun run dev
```

Open <http://localhost:4321>. Astro reloads modified pages. To develop the Rust
application alongside the site, run `trunk serve` in `crates/op-app/`; the combined
application is available in the production preview.

```sh
bun run build
bun test
bun run preview
```

The build checks TypeScript/Astro, generates the site and compiles the app with
Trunk into `dist/app/`. It requires Rust and `wasm32-unknown-unknown`. On Linux x64,
the script installs missing Rust/Trunk 0.22.1 into ignored `.tools/` without
modifying shell profiles. On Windows/macOS, install Rust and Trunk first.

`bun run build:site` and `bun run build:app` rebuild parts separately. The former
recreates `dist/`, so run it first. Preview serves the final folder: English `/`,
French `/fr/`, Spanish `/es/`, app `/app/`. English is the original site copy and
default root language; localized routes remain supported.

## Cloudflare Pages

Connect `linventif/open-process` to a **Pages** project:

| Setting | Value |
| --- | --- |
| Production branch | `main` |
| Framework | Astro |
| Root directory | `website` |
| Build command | `bun install --frozen-lockfile && bun run build` |
| Output directory | `dist` |
| `BUN_VERSION` | `1.4.0` |
| `NODE_VERSION` | `24` |
| Custom domain | `open-process.linv.dev` |

Set the domain through **Custom domains**. The build contains both parts; no
second project or `/app/` proxy is needed. Initial compilation downloads the Rust
toolchain and dependencies.

The production origin is configured in `src/lib/site.ts`. Optional `SITE_URL`
replaces it with another HTTPS origin. Cloudflare previews keep production
canonical URLs and emit `noindex` plus a disallowing `robots.txt`. You can also
use **Direct Upload** with `dist/` after `bun run build`.

References: [Astro on Cloudflare](https://docs.astro.build/en/guides/deploy/cloudflare/)
and [Pages build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/).

## SEO and content

- Build-generated English/French/Spanish HTML: titles, descriptions, content and
  links remain readable without JavaScript.
- Canonical URLs, English/French/Spanish/x-default `hreflang`, Open Graph and Twitter cards.
- `SoftwareApplication` structured data with licenses, free pricing and app link.
- Generated `sitemap-index.xml`, localized sitemap and `robots.txt`. The app and
  404 page are excluded from the sitemap; `/app/` has a `noindex` header.
- Bundled CSS/TypeScript with versioned names, WebP screenshots, explicit image
  dimensions, local Inter fonts and asset caching.
- Keyboard navigation, screenshot tabs and enlargement. A `details`/`summary`
  language dropdown shows EN/FR/ES, native language names, decorative flags and
  the selected language. Links work without JavaScript; with JavaScript, Escape
  or an outside click closes the menu. Shared `LanguageFlag.astro` uses local
  `public/flags/` SVGs, hidden from screen readers as decoration.

Translations live in `src/lib/messages.ts`, content in
`src/components/Landing.astro`, metadata in `src/layouts/Page.astro`, and behavior
in `src/scripts/site.ts`. `public/assets/` contains the logo, screenshots and font
licenses. `_headers` separates presentation-site policy from the app's WebAssembly
and generated scripts.

The transparent logo and favicons in `public/icons/` derive from shared native/web
vector artwork. See [the icon guide](../docs/icone.md) to regenerate formats.

## Downloads and CI/CD

A public GitHub API request loads the latest non-prerelease release. Links become
direct downloads when matching assets exist; otherwise they point to the release
page. No token is exposed to the browser.

| Platform | Asset |
| --- | --- |
| Windows x64 | `open-process-x86_64-pc-windows-msvc.exe` |
| Linux x64 | `open-process-x86_64-unknown-linux-gnu.tar.gz` |
| macOS Apple Silicon | `open-process-aarch64-apple-darwin.tar.gz` |
| macOS Intel | `open-process-x86_64-apple-darwin.tar.gz` |

macOS archives contain `Open Process.app` with Finder/Dock icons. Linux archives
include the binary, desktop launcher, icon and `install.sh` for user installation.
Standalone binaries remain fallbacks for releases without archives. The Windows
icon is embedded during compilation.

GitHub Actions checks the combined Pages build and Bun tests before native
release publication. Pushes to `main` publish `main-<run number>-<short SHA>` after
tests and four target builds succeed; `v*` tags are supported too. `main-*` builds
and prerelease tags remain prereleases; only `vMAJOR.MINOR.PATCH` becomes latest
stable. Release assets include `SHA256SUMS`. Dependency audits and executable
SQLite checks are part of CI; action versions are pinned to commits.
Cloudflare Pages is the deployment target and builds/deploys through its Git
integration. The GitHub Actions website job only validates the build and uploads
an artifact; it does not publish a site.

When retiring the former GitHub Pages site, disable its publishing source in
[the repository's Pages settings](https://github.com/linventif/open-process/settings/pages):
select **Deploy from a branch**, set **Branch** to **None**, then **Save**.
This repository setting is separate from workflow files, so removing an old
workflow alone does not disable branch-based Pages publishing. See
[GitHub's deletion guide](https://docs.github.com/en/pages/getting-started-with-github-pages/deleting-a-github-pages-site).

Bun tests check release links, three-language metadata, sitemaps and application
presence in the final output; output-dependent tests must follow the build.
Historical visual checks covered tabs, EN/FR navigation, screenshot dialog,
downloads and mobile layout. Spanish and EN/FR/ES links were checked by builds/HTML
tests, without an additional interactive browser validation for that addition.
See [the verification record](../docs/verification.md) for historical check scope.

After a complete build, an installed Firefox can run all four Wasm job types,
cancellation and error handling against the shipped app CSP:

```sh
python3 ../scripts/check-web-worker.py
python3 ../scripts/check-web-worker.py --smoke autosave --timeout 70
```

The checks use a temporary browser profile and a server bound to `127.0.0.1`.
The autosave check exercises the real app, local-storage writes, page hiding,
quota failure/retry and reopening after a reload.
For Snap-packaged Firefox it uses the direct executable to avoid launcher/profile
namespace restrictions; `--firefox PATH` selects another executable. This is an
explicit local check, not a step currently run by CI.
A standalone Trunk build at `/` can use `--dist PATH --app-prefix /` to check the
same transport and CSP with root asset URLs.
